## Приоритетное уточнение пользователя: ROOT ведёт проект, TechLead — реализацию

ROOT не назначает конкретные проверки, сценарии реплик или последовательность технических задач. TechLead отвечает за доставку пользовательской возможности целиком и сам выбирает реализацию, испытания и рутинные следующие шаги. ROOT решает продуктовые приоритеты, существенные бюджеты и смену стратегии; не требует возврата за разрешением на каждую следующую задачу. Алиса — средство автономной приёмки, конечная цель — пригодный компаньон.

ROOT не согласовывает отдельные правки, скрипты, проверки, параметры, гейты и технические сроки до секунд. Это полномочия TechLead внутри согласованной цели и действующих ограничений. Активные работы из-за смены уровня управления не прерываются. ROOT отвечает за продуктовые рубежи, приоритеты, общие затраты, распределение ресурсов, сохранение уже работающего и решение stop/pivot/rollback при отсутствии отдачи.

Ближайший рубеж — оставленный в эксплуатации компаньон с инициативой и пригодным обычным общением. Следующие рубежи — восстановленное штатное движение и полный целевой дизайн (осмысленное наблюдение, цели, память, персона, инфраструктура); первый рабочий шаг не заменяет проект. Технический порядок выбирает TechLead. Все прежние требования остаются в реестре.

Сводка для ROOT — максимум пять строк: новая/потерянная пользовательская возможность; состояние рубежа и главный пробел; активное время и риск; одно требуемое управленческое решение с ценой/fallback; следующий продуктовый результат/ETA. Технические логи, PID, hashes, API-поля и подробности проверки остаются у TechLead. Эскалация ROOT нужна при смене цели/стратегии/бюджета, потере функции, внешнем блокере либо 30 мин без новой возможности/двух неуспехах подхода, а не при каждой обычной правке. Заранее обоснованные длинные работы имеют собственный проектный лимит. Фактические tool-denials, STOP/privacy/physical limits и один владелец стенда обязательны.

# Исправленный режим управления

Причина изменения: техническая декомпозиция и количество проверок подменили достижение работающего продукта. Руководитель не остановил расход усилий вовремя.

1. Root отвечает за результат и цену достижения, TechLead — за технический путь и специалистов. Два диспетчера одних исполнителей запрещены.
2. Одна интеграционная цель одновременно; максимум одна необходимая параллельная source-задача. Новая задача обязана иметь пользовательский outcome, владельца, timebox, stop condition и rollback.
3. План принимается только с ближайшим работающим результатом. Отчёт: что реально заработало/потеряно; чем подтверждено; потраченное время; решение; следующий outcome.
4. Нет результата30мин или две неудачные попытки одного подхода — остановить повтор и принять stop/pivot/rollback. Продолжение требует явной оценки ожидаемой пользы и лимита, не механического ещё одного теста. Заранее выбранный meaningful длительный тест имеет собственный лимит.
5. Готовый baseline предпочтительнее собственной реализации. Не создавать новый слой до доказанного ограничения существующего. Рабочий fallback сохранять и возвращать при регрессии.
6. Приёмка по включённой пользовательской функции и эксплуатационному handoff. Тесты подтверждают риски, не служат самостоятельной целью. Отдельный review — для существенного риска/законченного среза, не автоматически каждой обратимой правки.
7. Не выключать полезные готовые функции по окончании теста. Удалять тестовые артефакты; сохранять согласованный эксплуатационный режим. Реальные конфликты владельцев, STOP/privacy и физические пределы не игнорировать.
8. Root читает TechLead, не реализации/логи специалистов. Технические подробности остаются у исполнителей. Проверка затрат и решения фиксируются в PROJECT, техническое состояние — в TECH-STATUS.
9. Незавершённый полный дизайн остаётся backlog; временный baseline не объявлять всем проектом. Внешний blocker должен быть конкретным, с unaffected работой и минимальным действием для снятия.

10. После выявленного смешения R33/R34: ОДИН bounded аппаратный scope = ОТДЕЛЬНЫЙ новый чат. Операторские mega-чаты не переиспользовать для следующей задачи. Старый чат завершается known handoff и остаётся parked; поздние ответы на его закрытые вопросы маршрутизируются TechLead, не возобновляют автоматически закрытый arm/experiment. Fresh baseline/однацель/owner/timebox/stop/rollback передаются без истории десятков сцен. Source-чаты также заменять при смене области/росте контекста. Единственныйphysicalowner меняется только после реального release. TechLead организует это автономно.

11. Прямое новое указание человека в чате исполнителя имеет приоритет над старым техническим scope. TechLead сразу синхронизирует PRODUCT/currentowner/deadline с root; это не неавторизованный «поздний ответ». Не насильно закрывать активный человеческий чат ради процедурного разделения; отдельные новые scope-чаты создавать при следующем handoff. Метаданные PCM не называть доказанной человеческой речью без соответствующего свидетельства.
