# P0 первое «Алиса»: source-only подготовка, без аппаратных действий

TechLead, один непересекающийся read-only scope параллельно R34. Ни устройств, ни установок, ни voice/model запросов; production source не изменён.

**Подтверждённый путь:** frozen worker224ff166… `audio_events` сначала добавляет canonical prefix к первому непустому сегменту, затем Piper→Sox pitch/EQ→PCMchunks. Agent3a5e… явно передаёт prefix и открывает новый aplay при первомPCM. После каждого положительного write продвигает byte clock. Existing telemetry прямо помечает consumption/acoustic verification=false. Наличие «Алиса» в metadata и запись байтов в pipe не доказывают слышимое начало. Continuouscapture маскирует output/tail; отдельного акустического подтверждения wake-word здесь нет.

**Неустановленная причина:** источник потери первого слова пока UNKNOWN. Из этих исходников нельзя выбрать между сформированным PCM, потерей/переходом в playback и физическим стартом выхода/распознаванием колонки. Default prefix worker менять не требуется только из-за его значения: актуальный Agent передаёт explicitprefix. Никаких новых форматов/повторов обращения/модельных prompt-вариантов.

**Ближайший voice scope после R34:** одна ограниченная реальная фраза существующим production-путём; сопоставить начало localTTS/streamPCM и начало физического выхода в LAN, подтвердить фактическое включение Алисы по её ответу. Rawaudio/text наружу не экспортировать, пользователя QA не назначать, дополнительную LLM/VLM для верификации не запускать. Существующие byte timings использовать как транспортные границы, без ложной акустической трактовки. По одному установленному месту потери — одно минимальное исправление и один сценарий приёмки, с exactbackup/STOP/no lateoutput и сохранением +2dB. Если факт не получен — одна UNKNOWN/fallback квитанция вместо новой волны. Конкретная правка пока не выбрана и не реализована.
