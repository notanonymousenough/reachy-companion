# Локальный доступ без VPN

На роботе действует `security.robot.policy: local_ssh`. Firewall не доверяет
адресу хаба, подсети, SSID или MAC-адресу клиента. Политика `legacy_hub` сохранена
только для совместимости старых конфигураций; новые конфигурации используют
`local_ssh`. Исторический флаг `restrict_to_hub` пока включает установку firewall,
но при `local_ssh` не задаёт список разрешённых источников.

## SSH и API

Mac входит на робот (`pollen`) и хаб (`deploy`) своим существующим SSH-ключом.
На обоих устройствах парольный и интерактивный SSH-вход отключены, root по SSH
запрещён. Проверенные host keys закреплены; автоматического принятия новых ключей
нет. Заводской пароль не является способом сетевого восстановления. Не удаляйте
единственный авторизованный ключ: храните резервную копию своего приватного ключа
в защищённом месте. Эта настройка не меняет пароль локальной учётной записи.

На хабе работает `reachy-robot-tunnel.service` из
`deploy/local-security/reachy-robot-tunnel.service`. Он находит `reachy-mini.local`
через локальное обнаружение, проверяет закреплённый SSH host key, аутентифицируется
отдельным ключом и переподключается после смены сети или перезапуска робота.
Приватный ключ создаётся на хабе и остаётся на хабе. Пользователь робота
`reachy-tunnel` не имеет sudo и интерактивной оболочки; ключ разрешает пересылку
только в `127.0.0.1:8000` и `127.0.0.1:8090`. У сервера для него разрешена только
локальная пересылка (`AllowTcpForwarding local`), выполнение команд запрещено.

Хаб использует `network.robot_url=http://127.0.0.1:18000` и
`network.agent_url=http://127.0.0.1:18090`. Оба слушателя доступны только на loopback.
Токен Agent сохранён: SSH-туннель шифрует транспорт, токен проверяет API-запросы.

На этом Mac настроены проверенные алиасы:

```sh
ssh reachy-mini
ssh reachy-hub
./scripts/companion ssh robot -- hostname
```

Для локальных SDK/CLI, которым нужен прямой доступ к API, оставьте в отдельном
Терминале процесс:

```sh
./scripts/local-api-tunnel
```

После этого API доступны на Mac по `http://127.0.0.1:18000` и
`http://127.0.0.1:18090`. Не добавляйте `-g`, `GatewayPorts yes` или bind `0.0.0.0`.
Если клиент уже использует один из этих портов, остановите свой прежний туннель
или выберите другие локальные порты и согласованно измените клиентский конфиг.

ПК на момент настройки выключен. Его прежний прямой доступ к API робота больше
не разрешается firewall. Перед использованием голоса/камеры с ПК нужно настроить
там собственный SSH-туннель и URL клиента, затем проверить реальные потоки.
Произвольные прямые SDK/медиапорты не открываются автоматически.

Панель хаба на `http://reachy-hub.local:8080/control` остаётся доступна в LAN.
Эта работа не добавляет ей HTTPS и не меняет firewall хаба. Для шифрования доступа
к панели можно использовать SSH-пересылку с Mac на loopback хаба. Не публикуйте
панель или порты робота пробросом на интернет-маршрутизаторе.

## Правила робота

В обычной клиентской сети разрешены SSH TCP22, DHCP-клиент, IPv4/IPv6 ICMP и
multicast mDNS. Loopback и установленные соединения сохраняются. Прямые входящие
HTTP/SDK/медиаподключения, включая 8000/8090/8443/7447, блокируются. Исходящий
трафик эта таблица не фильтрует. Таблицы других служб не очищаются.

Для hotspot NetworkManager-dispatcher определяет **активный режим `ap`**, а не
название сети или адрес клиента, и добавляет соответствующий интерфейс в nft set
`recovery_interfaces`. На нём дополнительно разрешены DHCP-сервер (68→67), DNS и
заводские TCP8000/8443. Наш Agent8090 остаётся закрытым снаружи. При выходе из AP
интерфейс удаляется из набора. Эти исключения работают и для другого адреса
hotspot. Переключение Bluetooth → hotspot требует авторизации робота по PIN;
сеть hotspot должна иметь защищённый пароль.

Dispatcher установлен в `/etc/NetworkManager/dispatcher.d/70-reachy-firewall`,
включая ссылки для pre-up/pre-down. Firewall запускается до сети; начальный набор
AP-интерфейсов определяется при применении, затем обновляется событиями NM.
Перезапуск firewall в уже активном hotspot также сохраняет режим восстановления.
Ошибка чтения состояния NM оставляет API закрытыми; SSH по ключам не зависит от NM.

## После переезда

1. Подключить Reachy и хаб к одному доступному Wi-Fi. Для первичной настройки
   Reachy использовать Bluetooth → hotspot и заводской интерфейс настройки.
2. Если DHCP не выдал Mac адрес hotspot, проверить его состояние по Bluetooth и
   при необходимости временно назначить Mac адрес в подсети, которую сообщил робот.
3. В hotspot SSH по существующему ключу доступен по адресу робота, который сообщает
   Bluetooth. При числовом адресе передайте тот же `HostKeyAlias=reachy-mini-device`
   и проверенный файл known_hosts из настройки SSH; не отключайте проверку ключа.
4. После подключения обоих устройств к обычной сети проверить `ssh reachy-mini`,
   `ssh reachy-hub` и состояние туннеля. Фиксировать прежние LAN-адреса не нужно.

mDNS работает в одной multicast-доступной локальной сети. Изоляция клиентов,
разные VLAN или captive portal могут мешать соединениям. В этом случае используйте
собственный hotspot/маршрутизатор; отсутствие интернета само по себе не мешает
SSH, firewall и локальной связи. Переезд не гарантирует работоспособность без
подключения устройств к доступной сети.

## Изменение правил и диагностика

Перед отключением парольного входа нужно проверить ключ **новым** SSH-сеансом.
Установка firewall выполняет nft syntax check и ставит уникальный таймер отката:

```sh
sudo ./scripts/companion firewall install
# В отдельном новом SSH-сеансе проверить вход и оба API через туннель хаба.
sudo ./scripts/companion firewall confirm
```

Без подтверждения firewall автоматически отключится. `confirm` откажется
подтверждать уже истёкший таймер. При повторном `arm` предыдущий ожидающий таймер
отменяется, чтобы он не отключил позднее уже подтверждённые правила.

```sh
sudo nft list table inet reachy_companion
sudo systemctl status reachy-companion-firewall
# На хабе:
systemctl status reachy-robot-tunnel
journalctl -u reachy-robot-tunnel -n 30
```

Выполненные проверки: новые SSH-сеансы по ключам на обоих устройствах, запрет
парольной авторизации, доступ к API через туннель, блокировка прямого LAN-доступа,
реальный переход робота в AP с адресом 10.42.0.1 и возврат в клиентский режим с
закрытием исключений. Пакетные проверки IPv4/IPv6, TCP и DHCP выполняются отдельно
в изолированных Linux network namespaces скриптом `tests/live/local_firewall_packets.py`
(требует root и JSON с `rules` на stdin). Полная перезагрузка устройств и реальный
голосовой/видеопоток с выключенного ПК не проверялись.
